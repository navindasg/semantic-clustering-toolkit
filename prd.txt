PRD: Semantic Clustering Toolkit
Oct 5, 2026 · @Navin Dasgupta
Summary
The toolkit groups a stream of short text items into semantic clusters. Each cluster stays open while new items keep arriving and closes after a configurable quiet period. It runs end to end on a CPU/RAM-only laptop in demo mode, and moves to production by swapping storage and scheduling adapters, not by rewriting the core.
It is domain-agnostic. Each item is just text, a timestamp, an ID and optional metadata, so the same engine fits complaints, support tickets, feedback, alerts or any similar stream. "toolkit" is a placeholder name throughout.
Problem
Teams need to know when many people are reporting the same thing, and when that thing has gone quiet. One-off batch clustering (embed, then HDBSCAN) tells you what topics exist in a fixed dataset, but it breaks on a live stream in three ways:
• Cluster IDs change on every run, so nothing downstream can track a cluster over time.
• A new item can't join an existing cluster without refitting everything.
• There is no notion of a cluster being active, quiet or resolved.
The toolkit keeps batch clustering for discovering new topics and adds a stable, incremental layer for assignment and lifecycle on top of it.
Goals and non-goals
v1 succeeds if an integrator can point a stream at the toolkit and get stable, trackable clusters with a lifecycle, on a laptop, in an afternoon.
Goals
• Assign each incoming item to an existing cluster, or hold it for discovery, in a single call.
• Discover new clusters from unassigned items without disturbing existing ones.
• Track each cluster's lifecycle: open, close on inactivity, reopen within a grace window, merge duplicates.
• Return a representative sample of any cluster for review or labeling.
• Run fully locally on a CPU-only laptop, with no PyTorch in the default install.
• Scale to production by swapping adapters, with the same engine and config.
Non-goals for v1
• Training or fine-tuning embedding models.
• A ticketing or case-management UI. The toolkit emits events; other systems own the workflow.
• Multi-label assignment. Each item belongs to at most one cluster.
• Streaming transport (queues, brokers). Callers bring their own and hand the toolkit batches.
• Root-cause analysis or suggested resolutions.

Core concepts
All cluster state lives in raw embedding space, so it stays valid no matter how often discovery reruns.
Term
What it is
Item
One text record: ID, text, event timestamp, optional metadata. Immutable once ingested.
Embedding
A fixed-length vector for an item, tagged with the ID of the model that made it.
Cluster
A group of items about the same thing, with a permanent ID, status, counts, first and last seen times, and a label.
Exemplars
A fixed-size sample of a cluster's embeddings (default 32) used to match new items. Refreshed by reservoir sampling as the cluster grows.
Threshold
The similarity a new item must reach to join a cluster. Set per cluster from its own spread at discovery time.
Buffer
Items that matched no cluster, waiting for the next discovery run.
Orphan
A buffered item that aged out without ever forming a cluster.
A cluster moves through four states:
Only open and recently closed clusters are matched against new items. Archived and merged clusters stay in the store for history and reporting.
How it works
The engine runs three jobs that share one store: assignment on every batch, discovery on a schedule, and a sweep on a schedule.
The dashed line is all the hot path reads from the store: each cluster's exemplars and threshold. A match writes back only the item, the cluster's count and its last-seen time.
1. Assign (every batch). Embed the items, then score each one against the exemplars of open clusters and of closed clusters still inside the grace window. The score is the mean cosine similarity of the top-k closest exemplars. If the best score clears that cluster's threshold, the item joins it and last_seen updates. Otherwise it goes to the buffer.
2. Discover (hourly, or when the buffer fills). Snapshot the buffer, reduce it with UMAP, and cluster it with HDBSCAN. Each candidate cluster is first checked against existing open clusters and folded in if it overlaps. The rest become new open clusters with a permanent ID, sampled exemplars and their own threshold. Noise stays in the buffer, and items that arrived during the run are re-assigned afterward.
3. Sweep (every few minutes). Close open clusters that have been quiet for close_after, archive closed clusters past reopen_grace, run the merge check, and turn buffered items older than buffer_max_age into orphans.
UMAP only exists inside discovery. Matching always happens in raw embedding space, which is what keeps cluster IDs stable when discovery reruns.

Demo mode
Demo mode runs the full engine on one laptop: a SQLite file, an in-process scheduler, a simulated clock and a bundled dataset. One command replays a stream fast enough to watch clusters open, grow and close in a few minutes.
• Sample dataset. Synthetic short-text items with timestamps and hidden ground-truth topic labels. Topics arrive in bursts and then go quiet, so every lifecycle state shows up.
• Bring your own data. Any CSV or JSONL with a text column and a timestamp column; column names are configurable.
• Simulated clock. Replays items in event-time order at a chosen speed. Discovery and sweeps fire on simulated time, so a week of data plays out in minutes.
• Live event log. The terminal prints each open, close, reopen and merge as it happens.
• Report. One static HTML file: a cluster table (status, size, label, first and last seen), a timeline of when each cluster was open, a 2D map of items colored by cluster, and sampled items per cluster.
• Scoring. When the data carries ground-truth labels, the report adds the metrics from Success metrics.
uv pip install "toolkit[demo]"
toolkit demo run --data sample --speed 3600 --close-after 2d   # 1 simulated hour per second
toolkit demo report --out report.html
Demo mode uses the same engine as production; only the store, scheduler, clock and event sink adapters change. No data leaves the machine after the model download, and no LLM is called unless one is configured.

Success metrics and evaluation
Quality is measured by replaying labeled data through the same engine, so every metric can be computed in demo mode. Targets get set after the first baseline run on representative data.
Metric
What it measures
Assignment precision
Share of assigned items whose cluster's majority true topic matches their own
False merge rate
Share of clusters that mix two or more true topics
Fragmentation
Clusters per true topic; 1.0 is ideal
Time to detect
Event time from a topic's first item to its cluster opening
Orphan rate
Share of items that never join a cluster
Close lag
Time from a topic's real last item to its cluster closing, compared with close_after
Throughput and latency
Items per second, and p95 assignment latency
The evaluation harness ships with the toolkit. toolkit eval replays a labeled file and prints these metrics. toolkit tune sweeps thresholds and HDBSCAN settings over the same file and shows the trade-off between false merges and fragmentation, which is the main dial.
Milestones
Five milestones, each closed by an exit check. Milestones 1 to 3 deliver a working demo; 4 and 5 make it production-ready.
1. Core engine. Embedder interface, assignment and discovery on an in-memory store, unit tests.
    ◦ Exit: running assignment and discovery twice on a fixed dataset gives the same cluster IDs.
2. Lifecycle and storage. Clock interface, sweep, reopen, merge, SQLite store, CLI.
    ◦ Exit: replaying the same dataset twice yields an identical event log.
3. Demo mode. Sample dataset, replay runner, terminal event log, HTML report.
    ◦ Exit: a fresh laptop goes from install to report in three commands.
4. Evaluation. Labeled replay, metrics, tuning tool, performance checks against the non-functional targets.
    ◦ Exit: baseline metrics and targets recorded for the default model.
5. Production adapters. Postgres and pgvector, worker scheduling, webhooks, HTTP endpoint, operator overrides, LLM labeler plugin.
    ◦ Exit: the same replay produces matching results on SQLite and Postgres.
Risks and mitigations
The biggest risk is threshold calibration, because it decides both false merges and fragmentation.
Risk
Mitigation
Thresholds set wrong, so unrelated items merge or one topic splits into many clusters
Per-cluster thresholds with global bounds; the tuning tool; the merge check
Stray matches keep a cluster open long after its topic ended
keep_open_min_items activity floor; close lag tracked as a metric
A topic's wording drifts over time, so new items stop matching
Exemplar refresh by reservoir sampling; merge and split overrides
Changing the embedding model invalidates every cluster
Model ID pinned on every vector; migration command re-embeds exemplars
New topics surface late because the buffer is too small for HDBSCAN
Size-based discovery trigger; lower min_cluster_size; time to detect tracked

Seeded runs; cluster state lives in raw embedding space, so variance only touches discovery
Locked-down machines block package or model downloads
Local model paths; an offline bundle of wheels and models
Items contain sensitive text
Preprocessing hook for redaction; local-only demo; no LLM by default
